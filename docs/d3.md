# D3.js dashboard prototype

## Summary

A first-pass prototype dashboard built with [D3.js v7.9.0](https://d3js.org/). The same four
charts are rendered from the same synthetic outbreak dataset as the Plotly.js and Chart.js
prototypes, so the three libraries can be compared like for like.

Routes: `GET /dashboard/d3` (overview) and `GET /dashboard/d3/{chartId}` (expanded with filters).

## Fit with GOV.UK and APHA

D3 renders SVG directly in the DOM, which gives complete control over every visual element —
GDS Transport fonts, the GOV.UK palette, focus states and print stylesheets are all straightforward
because nothing is hidden inside a canvas context or a library-owned shadow DOM. GOV.UK colours are
applied exactly as supplied by the view model; no theme overrides are needed, and SVG scales
cleanly without pixellation.

The real cost is that D3 is a low-level data-visualisation toolkit, not a chart library. There are
no built-in chart types: every axis, legend, tooltip and responsive behaviour must be designed,
written and maintained by hand. `dashboard-d3.js` is **415 lines** to render four simple chart
types (line, bar, stacked bar, doughnut). The equivalent Chart.js or Plotly configuration for the
same charts is a fraction of that length. Any future chart type, interaction pattern or layout
change requires D3-specific knowledge and bespoke implementation. Bug fixes, edge-case handling
(legend overflow, tick density, narrow-viewport behaviour) and accessibility enhancements all
accumulate as custom code that the team must own long-term.

There is no GOV.UK Design System integration guide for D3; the team would have to establish and
document its own conventions. By comparison, batteries-included libraries ship sensible defaults
and handle the long tail of edge cases that this prototype has not yet encountered.

D3's `selection.style()` API can inject inline styles; care is needed to avoid CSP violations (see
the accessibility section below).

## Bundle size

| Metric                           | Value        |
| -------------------------------- | ------------ |
| Raw chunk (`dashboardD3-*.js`)   | **78.97 kB** |
| Gzipped                          | **26.54 kB** |
| Baseline `application.js` (raw)  | 9.85 kB      |
| D3 addition over baseline (raw)  | **+69.1 kB** |
| D3 addition over baseline (gzip) | **+23.4 kB** |

The bulk of the bundle is the D3 package itself, tree-shaken from the monorepo so only the modules
actually used are included. The chart-rendering code adds negligible overhead.

Compared with Chart.js (~60 kB gzip) and Plotly.js (~200 kB+ gzip), D3 sits in the middle for
bundle size when a full set of chart types is required.

## Accessibility

**SVG vs canvas.** D3 produces SVG, which lives in the DOM and is in principle inspectable by
assistive technology — individual elements can carry `aria-label`, `role`, `title` and `desc`
attributes. Canvas-based libraries (Chart.js by default) cannot expose chart internals to the
accessibility tree at all without separate workarounds. This is a genuine structural advantage of
SVG.

**What this prototype exposes.** None of that potential is exercised here. The SVG produced by this
prototype carries `aria-hidden="true"` and `focusable="false"` on every element, deliberately
hiding the chart internals from assistive technology. No data points, axes or labels are announced
to screen readers. There is no keyboard interaction with individual data points.

**How the gap is mitigated.** Two complementary mechanisms compensate:

1. Each chart mount carries `role="img"` and a descriptive `aria-label` (e.g. "Weekly new cases.
   Total new cases reported each week. The same information is available in the data table below.")
   — provided by the shared `chart-card.njk` partial, not by D3 code.
2. A `govuk-details` disclosure widget immediately below each chart renders the full dataset as a
   GOV.UK table, giving screen reader and keyboard users access to the same information.

**WCAG 2.2 AA assessment.** This approach would satisfy the non-text content criterion (1.1.1) via
the `role="img"` + `aria-label` text alternative, and keyboard access to the data is met by the
data table link. It would not satisfy a strict reading of success criteria that require chart data
points to be individually keyboard-operable or announced (there is no relevant WCAG 2.2 criterion
that mandates this for supplementary charts paired with a data table, but an auditor applying GDS
service standards could flag the lack of individual-point keyboard access as a usability concern).
Tooltips, if added, would need to be keyboard-accessible and not rely solely on pointer hover.
The paired data table is the approach recommended by the GDS accessibility team for charts.

**CSP.** No inline styles are injected. D3 `attr()` methods are used throughout. The one DOM
property set directly (`element.style.cursor = 'pointer'`) does not write an inline `style`
attribute and does not require `style-src 'unsafe-inline'`. The existing `style-src 'self'` policy
is unchanged and unrelaxed.

**Responsive.** `ResizeObserver` re-renders charts when the container resizes; no viewport-specific
code path means the same SVG serves both the 260 px card and the 440 px expanded view.

## How it is used in this prototype

1. `src/client/javascripts/dashboard-d3.js` is the Vite entry point. On page load it:
   - Queries all `.app-chart` mounts.
   - Reads the sibling `<script type="application/json">` data block for each chart.
   - Dispatches to `renderLine`, `renderBar`, `renderStackedBar`, or `renderDoughnut` based on
     `data-chart-type`.
   - Attaches a `ResizeObserver` to each mount for responsive re-render.
2. `src/server/routes/dashboard-d3/` holds the Hapi plugin (`index.js`), two controllers
   (`controller.js`), two Nunjucks views (`index.njk`, `expanded.njk`) that extend the shared
   foundation partials, and controller tests (`controller.test.js`).
3. The route plugin is registered alongside `home` and `about` in
   `src/server/plugins/router.js`.

## Suggested iterations

- **Tooltips**: D3 has no built-in tooltip; a follow-up would add pointer event handlers that
  position a `<div>` tooltip for hovered data points. Ensure the tooltip content is also present in
  the data table rather than being the sole source of that information. Tooltips must also be
  keyboard-accessible to avoid introducing new accessibility failures.
- **Transitions**: D3's transition API can animate bar growth and line draws on initial render.
  Provide a `prefers-reduced-motion` check before enabling transitions.
- **Axis label text**: Currently rotated tick labels on the date axis can overflow on narrow
  viewports; a follow-up should truncate or thin ticks further at small widths.
- **Legend overflow**: The legend row-wrap logic in the doughnut chart is approximate; a proper
  `foreignObject` or multi-row layout would be more robust.
- **Shared scale helpers**: The three series-based charts (line, bar, stacked-bar) each rebuild
  their scales independently. Extracting `buildXScale` / `buildYScale` helpers would reduce
  duplication and make it easier to enforce consistent padding.
- **Tree-shaking**: Only a subset of D3 sub-packages is used. Importing directly from
  `d3-scale`, `d3-selection`, `d3-shape`, etc. rather than from the top-level `d3` package would
  further reduce the bundle.
